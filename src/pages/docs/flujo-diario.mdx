# El Flujo de Trabajo Diario: Guardar y Sincronizar Código

Una vez que dominas el modelo mental de Git, el ciclo de vida de tu código en solitario se convierte en una rutina lógica de tres pasos que te permitirá guardar tus avances de forma incremental y segura.

---

## 1. El Ciclo de Vida del Código en Solitario

El flujo de trabajo diario consiste en transicionar tus archivos a través de los tres estados de Git:

1.  **Modificar:** Editas código en tu directorio de trabajo (*working directory*).
2.  **Preparar:** Seleccionas y añades tus cambios listos al área de preparación (*staging area*).
3.  **Confirmar:** Tomas la copia instantánea permanente en tu repositorio local (*local repository*).

---

## 2. Diagnóstico Constante: El uso de `git status`

Para evitar trabajar a ciegas, Git proporciona un comando de diagnóstico indispensable que debes ejecutar constantemente:

```bash
git status
```

Este comando inspecciona tu árbol de trabajo (*working tree*) y te muestra con precisión:
*   Qué archivos han sido modificados pero aún no han sido agregados al área de preparación.
*   Qué archivos están preparados para ir en tu próxima confirmación (*staged*).
*   Qué archivos de tu carpeta no están siendo rastreados por Git (*untracked files*).

---

## 3. Preparando Cambios: `git add`

Para mover tus modificaciones desde el directorio de trabajo hacia el área de preparación (*staging area*), utilizas el comando `git add`. Tienes dos formas de usarlo según tu necesidad:

*   **Preparar un archivo específico:** Ideal para mantener confirmaciones limpias y enfocadas.
    ```bash
    git add ruta/al/archivo.js
    ```
*   **Preparar todos los cambios:** Añade todas las modificaciones del directorio actual de forma masiva.
    ```bash
    git add .
    ```

---

## 4. Guardar Cambios en el Repositorio: `git commit -m`

Cuando tus archivos modificados ya están listos en el área de preparación (*staging area*), es momento de confirmarlos para almacenarlos permanentemente en tu base de datos de Git. Para crear un commit (*commit*), utiliza:

```bash
git commit -m "feat: agregar sistema de login de usuarios"
```

### Convenciones de Mensajes Semánticos
Para mantener un historial de confirmaciones (*commit history*) ordenado y profesional que tu equipo y tú puedan entender con facilidad en el futuro, es una excelente práctica utilizar mensajes semánticos (*semantic commits*). La estructura sugerida es `<tipo>: <descripción corta en minúsculas>`:

*   `feat`: Nueva funcionalidad de software (ej. `feat: agregar pasarela de pago`).
*   `fix`: Solución de un error o bug (ej. `fix: corregir redireccion de logout`).
*   `docs`: Cambios únicamente en la documentación (ej. `docs: actualizar readme de instalacion`).
*   `chore`: Tareas de mantenimiento o dependencias que no modifican el código de producción (ej. `chore: actualizar libreria de estilos`).

---

## 5. Sincronizar hacia el Repositorio Remoto: `git push`

Tus confirmaciones locales están a salvo en tu disco. Sin embargo, para compartirlas con tu equipo o respaldarlas en la nube, debes empujar tus cambios al servidor remoto (*remote repository*) en GitHub o GitLab:

```bash
git push origin main
```

*(Donde `origin` representa la conexión al servidor de alojamiento remoto y `main` es el nombre de la rama que estás sincronizando).*

> **💡 Consejo de Senior:** Usa `git status` como tu panel de control principal. Acostúmbrate a ejecutarlo antes y después de cada `git add` y `git commit`. Te ahorrará subir archivos temporales, dependencias pesadas o credenciales sensibles al área de preparación (*staging area*) por error.
